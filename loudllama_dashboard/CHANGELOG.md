# Changelog

## 0.10.016

- Fix: **on a wide/wall-mounted screen, widgets now looked visibly stretched out of proportion - a 2x2 widget sized for two square-ish cells rendered noticeably wider than it was tall**, reported directly from a screenshot right after 0.10.015 let the grid reach a wide screen's full width. Root cause: `columnOpts` (createPage() in app.js) already has the grid pick its own column *count* from the screen's width, specifically so each column stays close to a fixed ~90px (the same comment already explained this adapts a phone down to ~4 columns so a compact tile doesn't get crushed too thin) - but that picking was capped at 12 columns no matter what (`columnMax: 12`), a ceiling that was easy to miss because `--llw-max-content-width` (removed in 0.10.015) was separately capping the grid's own width to roughly the same ballpark anyway, so a screen past ~1080px wide never actually got more than its original 12 columns - they just had to stretch wider to fill whatever space they were given, invisibly so right up until 0.10.015 let that space reach a real wide screen's actual edges. Raised `columnMax` to 40 (covers true ~90px columns up to 3600px-wide screens before it has to clamp the same way 12 used to). GridStack has no built-in CSS to size/position items past 12 columns on its own (same reason it ships its own `gridstack-extra.css` just to cover 2-11) - a new, separately auto-generated `frontend/css/gridstack-wide.css` extends that same per-column-count width/position CSS up through 40, loaded from index.html right alongside GridStack's own extra stylesheet. Verified directly against the real dashboard this was reported on: forcing the same column recalculation this change makes automatic (a 2000px-wide screen landing on 22 columns instead of 12) renders a 2x2 widget as a true square again (181.8x180px, matching its own ~90.9px columns against the unchanged 90px row height) instead of stretched.

## 0.10.015

- Fix: **even after 0.10.014 stopped a dragged widget from visually vanishing, it still couldn't actually be *placed* in the empty space furthest left or right on a wide/wall-mounted screen - it would just snap straight back to wherever it started.** Confirmed directly (again live, against the actual wall-mounted dashboard this was reported on): that empty space was never part of the GridStack grid to begin with. 0.10.010 capped the grid at `--llw-max-content-width` (1600px) and centered the leftover space on a wide screen specifically so a sparse dashboard wouldn't render pinned to the top-left with a large, lopsided empty area down one side - but that centering margin sits entirely outside the grid's own element, so there's no column there to drop a widget on, no matter how far you drag it. Asked directly which tradeoff was preferred: the width cap is now removed entirely, so the grid always spans the full screen and every bit of it is real, placeable grid space - a sparse dashboard can in principle go back to rendering pinned toward one side the way it did before 0.10.010, until there are enough widgets to fill the screen out, but confirmed as clearly the preferred outcome over having unusable space on a wide screen. Verified directly: with the cap removed, a widget dragged all the way to either true screen edge now drops and lands there cleanly instead of bouncing back.

## 0.10.014

- Fix: **a widget being dragged could vanish into the background the moment it was dragged far enough left (or, symmetrically, past any other edge of the grid) - specifically reported as "I can't place a widget further left than wherever the camera widget already is, it's like the widget disappears under the background."** Root cause, confirmed both in an isolated local reproduction and directly against a real, live Home Assistant instance (forcing the dragged tile's own `pointer-events` back on so hit-testing couldn't be confused with it simply being temporarily click-through, which it normally is while dragging): GridStack moves the tile being dragged with `position: fixed` plus a very high z-index while a drag is in progress, which would normally make it track the real browser viewport and be exempt from any ancestor's clipping. But `goToPage()` keeps a live `transform` on the pages track at all times (even on a single-page dashboard, even sitting on page 0 - it's unconditional, not just applied while actually mid-swipe), and a `transform` on an ancestor is exactly what makes a browser re-home a `position: fixed` descendant to *that* ancestor's own box instead of the real viewport - which also means it's no longer exempt from that ancestor chain's own overflow clipping, the same as any ordinary absolutely-positioned element isn't. The pages viewport clips horizontally for an unrelated, legitimate reason (hiding the other, not-currently-shown pages of a multi-page dashboard) - on an ordinary laptop/phone screen that clip boundary sits right at the browser's own edge, where a real cursor could never reach anyway, so it's invisible in practice; it only becomes reachable once `--llw-max-content-width`'s centering kicks in on a wide screen (a wall-mounted panel, an ultrawide monitor) or whenever there's simply free grid space next to a screen edge to drag a widget past. Fixed narrowly: the pages viewport and the current page briefly stop clipping for exactly as long as a drag (or, for whenever free resizing returns, a resize) is actually in progress, so the drag ghost stays visible following the cursor the same way it already does everywhere else on the grid - GridStack still clamps the final dropped position to a real, valid cell regardless of how far outside the normal content box the cursor wandered while dragging.

## 0.10.013

- Fix: **the sidebar hairline from 0.10.012 was still there** after rebuilding and hard-refreshing - confirmed directly by connecting to a real, live Home Assistant instance and inspecting its actual DOM rather than guessing further from screenshots alone. The real cause turned out to be a third thing, different from both of 0.10.012's fixes: Home Assistant's sidebar is built on a Material-style "drawer" component (`ha-drawer`), and hiding `ha-sidebar` itself only hides the *content slotted into* that drawer - it does nothing to the drawer's own shadow-DOM wrapper that reserves the space for that slot (found live: `ha-drawer`'s shadow root keeps a `div.sidebar-shell`, exactly the sidebar's own width, with its own `border-right` - entirely independent of whether the sidebar content inside it is visible). That wrapper's right-hand border was the hairline. It's now found and collapsed too - by matching its width against the sidebar's own just-hidden width, the same geometry-based approach already used elsewhere here, rather than hard-coding a class name that isn't guaranteed stable across Home Assistant releases. Verified by applying the exact fix against that same live instance's real DOM: the sidebar wrapper now collapses to 0 width and its border disappears along with it, with nothing else on the page affected.

## 0.10.012

- Fix: **turning kiosk mode on left a thin vertical line running down the screen exactly where Home Assistant's sidebar used to be, and turning kiosk mode back off never actually brought the sidebar back** - confirmed directly against screenshots, reproducing with kiosk mode both on and off. Two separate bugs, found by reading applyKioskMode() end to end: (1) the toolbar's kiosk on/off button only ever called `window.location.reload()` - which only reloads *our own* page, the content sitting inside Home Assistant's Ingress `<iframe>`. Every DOM change applyKioskMode() makes (hiding the sidebar, rewriting the app-shell's own grid/flex layout, forcing the iframe full-bleed) happens on `window.top`'s document instead - Home Assistant's own top-level page around us - which that reload never touched at all, so turning kiosk mode off saved the setting and reloaded, yet every one of those changes just sat there, sidebar included. It now reloads `window.top.location` instead - the same actual browser tab Ingress is hosting us inside of - which reloads Home Assistant's whole UI from a clean slate, sidebar and all. (2) Some Home Assistant frontend versions render a separate, thin drag-to-resize handle right next to the sidebar, which hiding `ha-sidebar` itself never touched, leaving it behind as a stray hairline even with the sidebar itself correctly gone. It has no stable, version-proof element name the way `ha-sidebar` does, so it's now found by shape instead - an unmistakably thin, tall sibling bar right where the sidebar was - and hidden the same way. Verified directly with a synthetic Home Assistant shell reproducing both the resize-handle sibling and the reload-scoping bug: kiosk mode on now cleanly hides sidebar *and* handle with nothing left over, and toggling back off now genuinely restores the sidebar every time.

## 0.10.010

- Fix: **the dashboard's widgets could end up pinned to the top-left of a wide browser window, leaving a large, lopsided empty area down the right side** - reported as "still a kiosk mode problem," happening identically with kiosk mode on or off. It wasn't actually kiosk mode: `applyKioskMode()` returns immediately and touches nothing at all when the toggle is off, so whatever caused this had to be something else entirely running unconditionally. Root cause, confirmed directly by measuring the actual rendered grid: GridStack's own column system caps out at 12 columns (`columnOpts.columnMax`, unchanged since it was introduced) - on an ordinary laptop/tablet screen that's roughly the screen's own width, but on a much wider display (an ultrawide monitor, a big wall panel) the grid simply never grows past that natural ~12-column width, because nothing was telling it to stretch or center the leftover space - it just sat flush against the left edge instead, and a dashboard that doesn't yet have enough widgets to fill a row made the resulting empty strip very obvious. The grid's own container now caps at a sensible maximum width and centers itself once the screen is wider than that (a pure CSS change, `--llw-max-content-width` in app.css - see its own comment for why this had to be done on an ancestor element rather than as padding on the grid itself, a GridStack/absolute-positioning quirk). Ordinary screens under that width (most laptops, tablets, phones) are completely unaffected; verified directly across phone/laptop/ultrawide viewports and with multi-page swiping, 0 regressions.
- New: **Gøremål/indkøbsliste (To-do/shopping list) widget**, the last of the widgets asked for in the previous round. Full CRUD against one of Home Assistant's built-in `todo.*` lists (the classic Shopping list, or any other to-do list you've set up) - add an item, check it off (it sinks to the bottom with a strikethrough, same as any shopping-list app), or remove it, straight from the dashboard. A todo entity's items live behind Home Assistant *services* rather than in its own state/attributes the way most other domains work, so this needed its own small backend proxy (`GET /api/hass/todo_items/:entityId`, wrapping the `todo.get_items` service) alongside the generic service-call endpoint every other widget already uses for add/update/remove. Uses the same "optimistic UI, then reconcile shortly after" pattern the Room widget's own toggles use, so adding/checking/removing an item shows up instantly rather than waiting on a round trip.

## 0.10.009

- New: **Clock widget** - time and date, ticking once a second, no Home Assistant entity or setup required. Offers a full (2x2, time + weekday/date) and a compact (1x1, time only) size when added, and a settings panel to pick 12- or 24-hour format and whether to show seconds (12/24h defaults to whatever's conventional for the dashboard's own language).
- New: **Shortcuts widget** - a small grid of one-tap buttons, each wired to one Home Assistant scene or script ("Good night", "Movie night", etc). Pick which ones show from a checklist in its settings (the same checklist style the Cameras widget already uses for picking cameras); tapping a button just calls `scene.turn_on`/`script.turn_on` for that entity.
- New: **Who's home (People) widget** - lists every `person.*` entity with their photo and home/away status. Deliberately needs zero setup (shows everyone by default, unlike every other widget here); its settings let you hide specific people if you don't want all of them on this particular screen. Photos are proxied through the backend the same way camera snapshots already are (a `GET /api/hass/entity_picture/:entityId` endpoint) - a person with no photo set, or one this proxy can't resolve, gets a plain initials circle instead rather than a broken image.
- New: **Energy widget** - two independent, optional sensor readings side by side: "right now" (typically a power sensor) and "today" (typically a sensor that already accumulates its own daily total). Deliberately doesn't try to compute "today" itself from a lifetime-total energy sensor via Home Assistant's statistics API - that's a much bigger feature (reset detection, day-boundary handling, long-term-statistics fallback) than this widget is trying to be; pick whichever sensors your own setup already exposes for each.
- New: **Alarm widget**, controlling one `alarm_control_panel.*` entity (Alarmo and most others work). Asks once, right when you add it, whether it should be **simple** (one-tap arm/disarm, no code - meant for a screen inside the home) or **PIN code** (the same buttons, but each opens an on-screen keypad first and sends the entered code with the service call - meant for a phone or other device outside that physical trust boundary); changeable later from its own settings too. The same alarm entity can have one widget of each kind, since the mode lives on the widget, not the entity. This is also the first widget to ask a yes/no-style setup question that isn't about size - the "+ Add widget" menu's size-picker step (Light/Room/etc's full-vs-compact choice) now has a sibling, more generic "setup choice" step (`def.setupChoice` on `registerWidget`) that any future widget can reuse for its own one-off question.

## 0.10.008

- New: **kiosk mode now has its own on/off toggle in the toolbar** (🖥️, next to "Widgets"/"Home Assistant"), instead of always running unconditionally. Persisted server-side (a new `kioskMode` field alongside the background image in `/api/settings`, plus a small `POST /api/settings` endpoint to flip it), so it stays off (or on) across reloads/restarts rather than resetting. Flipping it reloads the dashboard, which is what cleanly applies or un-applies everything kiosk mode may have changed in Home Assistant's own DOM - trying to precisely reverse every `display:none`/grid-column/iframe-style tweak in place, live, would be a lot of fragile extra code for something a reload already does correctly for free.
- New: **kiosk mode now defers to whatever's already hidden Home Assistant's own sidebar**, rather than always doing its own hide-and-reclaim pass on it. Before touching `ha-sidebar`, it now checks whether the sidebar is already taking up zero space (already `display:none`, or already collapsed to a sliver) - if so, it leaves it alone entirely. This is specifically aimed at the well-maintained community "kiosk-mode" HACS integration some people already have installed and configured exactly how they want it: when that's present and has already dealt with the sidebar, this add-on's own kiosk logic now gets out of its way instead of potentially fighting it, and otherwise (no such integration, or it hasn't acted yet) runs its own hiding exactly as before. Deliberately checks the *effect* ("is it already gone?") rather than trying to specifically detect that one integration by name - any current or future mechanism that already clears the sidebar is deferred to the same way.
- Fix: **a persistent light-coloured strip down the left edge of the screen in a desktop web browser, surviving 0.10.004 through 0.10.007's attempts**. Those all centred on `fixIframeHeight()` (added in 0.10.007), which measures our own Ingress `<iframe>` against the real browser window and forces it full-bleed if it falls short - but it only ever checked the *bottom* edge (and, loosely, the top), on the assumption that any leftover gap would be a height problem. The reported gap was actually on the *left* edge instead (the iframe's own top/bottom lined up fine, its left edge didn't) - a case that check could never catch, so the fix simply never ran for it. It now also compares the iframe's left and right edges against the window's, and forces the same full-bleed fix for either case. Verified directly: a synthetic page reproducing the exact gap (a leftover 215px column pushing the iframe in from the left, matching the reported screenshot) is correctly pulled full-bleed now.
- Fix: **holding the screen for a moment anywhere on the dashboard made the "keep holding to edit" llama hint flash into view almost instantly**, reading as if the dashboard was about to jump into edit mode from an ordinary tap. The hold timer itself was always the full 2.5s either way - only the hint's *visibility* was tied directly to the press starting, with no delay at all. The hint now only starts fading in after a short, deliberate pause (350ms) once a press has been held that long; anything shorter (an ordinary tap, a scroll, a quick drag) never shows it at all. The fill animation's own timing was adjusted to match, so "the llama finishes filling" and "edit mode actually opens" still land at the exact same instant as before.
- Change: **compact (1x1) Room icons are noticeably bigger**, closer to how a real iOS/Android home-screen icon's artwork fills almost its entire rounded-square - reported as the icons still having "a slightly wrong size" even after 0.10.007's squircle corner-shape fix. The icon's own size (62% of its tile, capped at 64px) measured out to roughly half the tile with a wide empty margin all around; it's now 80% (capped at 90px), measured at roughly two-thirds of the tile. The dock-specific cap (for a compact room pinned to the bottom bar) was raised to match, re-verified side by side so a pinned room's icon still lands at very nearly the same size as the same room sitting on the grid.

## 0.10.007

- Confirmed: **dragging widgets in edit mode works again** after 0.10.006's removal of the legacy `-webkit-overflow-scrolling: touch` property - verified directly on a phone.
- Fix: **the remove (−) and pin (📌) buttons on a small 1x1 widget could sit close enough together to be hard to tell apart/hit the right one**. Both used to keep extra clearance from the bottom edge for a GridStack resize handle that doesn't exist any more (manual resizing was dropped in an earlier release in favour of each widget's own size picker) - that stale spacing was eating into the gap between the two buttons on a tile small enough for it to matter. Both now sit a plain, symmetric 6px from their own edge, matching each other.
- Fix: **pinning a compact 1x1 widget to the dock made its icon render noticeably bigger than it was on the grid**, not smaller as the dock's own scaling intends - confirmed directly: about 44px in the dock vs about 29-33px on the grid. Root cause: the dock tile's fixed box is larger than an ordinary 1x1 grid tile's own content area, so the icon's existing 62%-of-its-box sizing hit its maximum-size cap in the dock when it wouldn't have on the grid, and the dock's own zoom-out wasn't enough to compensate. The dock now caps that icon at a smaller size specifically, landing it back at very nearly the same size it is on the grid.
- New: **compact (1x1) Room/Light/Climate/Media icons use the same smoother "squircle" corner shape phone home-screen app icons use**, instead of a plain circular-arc rounded corner - directly compared side-by-side against a real phone home screen and asked for. Every other, bigger widget tile (Weather, Cameras, a room's full 2x2 view, etc.) is unaffected - this is specifically for the ones that function like an app icon.
- Fix: **the Weather widget's floating cloud/rain/snow animation could suddenly jump back to its starting position and restart**, roughly once a minute. The widget quietly re-renders on every routine 60-second refresh (to pick up a new temperature, etc.), and that render path was rebuilding the whole animated-particle layer from scratch every single time, even when the weather condition itself hadn't changed - instantly snapping every cloud back to frame one. It now only rebuilds that layer when the condition actually changes (sunny to rainy, etc.), which is the one case that should restart it; an ordinary temperature-only refresh now leaves the animation running undisturbed.
- Fix (best-effort, unverified): **a second attempt at the background not quite reaching the bottom of the screen in Home Assistant's mobile companion app**, which persisted through 0.10.003's and 0.10.006's CSS-only attempts. Both of those could only ever affect our own page's box - if Home Assistant's own frontend sizes the `<iframe>` our whole dashboard lives inside (Ingress) a little short of the actual screen height, no amount of `env(safe-area-inset-*)`/`100dvh` *inside* that iframe can paint over the gap between its bottom edge and the real bottom of the screen, because that empty space is outside the iframe entirely. Kiosk mode now also measures our own iframe against the top window's actual viewport and, if it falls short, forces it to a plain full-bleed fixed box instead. Same honest caveat as the rest of kiosk mode: reaches into Home Assistant's own unversioned frontend, can't be verified from this sandbox, best-effort only.

## 0.10.006

- Fix (best-effort): **dragging a widget to reposition it in edit mode**, confirmed to fail both in Home Assistant's mobile companion app and in a plain mobile browser - which rules out the companion app's own wrapper as the cause and points at the phone's browser engine itself. The page's scrollable area (`.llw-page`) was using the legacy `-webkit-overflow-scrolling: touch` property to get iOS's momentum scroll; every iOS version still in use today already scrolls smoothly without it, and it has a long-documented history of overriding a child element's own `touch-action` (exactly the `touch-action: none` edit mode sets on a widget so a touch-drag reaches GridStack instead of being read as a page scroll). Removed it. This sandbox can't fully reproduce real phone touch behaviour to prove the fix, so this is a reasoned best-effort attempt at a known class of bug, not a confirmed one - let me know whether dragging actually works now.

## 0.10.002

- Fix: **a widget could silently lose its own settings - most visibly the Weather widget's compact (2x2) size quietly turning back into the full forecast layout the next time the dashboard loaded**. Root cause: `saveConfig()`, the callback every widget calls to persist its own settings, replaces a widget's *entire* saved config outright rather than merging into it - but six widgets (Weather, Light, Thermostat, Speaker, Sensor, Cameras) called it with only the one field that had just changed (e.g. `{ entity_id: ... }` after picking an entity from a dropdown), silently dropping everything else that widget had saved, `sizeVariant` included. The widget kept looking right immediately afterward - the already-mounted widget never re-reads its own saved config - so the only sign anything was wrong was the *next* fresh load (a page reload, or restarting the mobile app) suddenly showing the old, wrong layout. All six now spread their existing config into `saveConfig()` instead of replacing it outright, so picking an entity (or, for Cameras, a camera) never touches any of a widget's other settings again.
- Change: **the Cameras (Frigate) widget no longer shows "Cameras" as a title above its camera grid** - it's self-evident what the widget is, and removing it means more of the tile is actual camera picture instead of a label. Its settings (⚙) button now sits alone in the top-right corner where the title used to share the row with it.
- Change: **holding the screen to reveal the edit toolbar now takes 2.5 seconds instead of 4.5**. Still deliberately longer than an ordinary tap or scroll could ever trigger by accident, just not as long a wait to actually get there.
- Change: **the "keep holding" cue for that gesture is now a small LoudLlama silhouette that fills in with colour from the bottom up as you hold**, instead of a plain growing ring - the same llama hidden as a subtle easter egg in the background art, just put to visible use here. It fills at exactly the pace of the hold itself, so it's finished right as edit mode opens.
- New: **popups now animate closed, not just open**. Room's live view and its setup screen, Frigate's live camera view, the widget store, and the Group widget's own folder-style bubble already popped in with a quick scale-up-and-fade (or, for Group, grew out of the tile you tapped); closing any of them - the × button, tapping the backdrop, or Escape - now plays that same motion in reverse before the popup actually leaves the screen, instead of just vanishing instantly. Group's card in particular shrinks back down toward the exact point it originally grew out of, rather than toward the screen centre.
- Fix: **every widget still showed a visible drop-shadow at its corners**, even after 0.09.017's fix tightened it to stop neighbouring shadows piling up into a square smudge - on an actual grid of widgets, a shadow that size was still clearly there at every corner. Widget tiles no longer have an outer drop-shadow at all, just the existing subtle inset highlight ring; nothing else (popups, the dock bar, state glows, decorative icon shading) was touched.
- Change: **the Room widget's front tile no longer lets you adjust the temperature directly** - the small +/- stepper next to the glance temperature is gone, since it sat right on top of "tap to open the room" and made the two easy to mis-trigger for each other. ## 0.09.021

- Change: **every device now has its own fully independent dashboard**. That meant removing a widget on your phone deleted it from that shared list, so it vanished from your PC's browser too, the wall-mounted tablet, everywhere - not what "remove this from my phone" should mean, and it got a lot more noticeable once the last couple of releases made it genuinely useful to shape your phone's dashboard differently from your PC's. - Fix: **every widget was still "too big" on a phone, regardless of its own grid size** - the actual root cause of the long-running mobile-sizing complaints this whole release is aimed at. The grid now stays a real multi-column grid at every width (disabling that legacy mode) and picks however many columns keep each column close to the same ~90px as a row's own height, so a cell stays roughly square on any device - a phone lands around 4 columns, a tablet or desktop around 12, same as before. - Fix: **a newly added widget could land far below the last row with a tall, empty-looking gap next to it**, even when there was open space right beside it. Every fresh widget was being added at a literal, requested (0, 0) - which made the grid's collision handling push it straight down the same column past whatever was already there, instead of sliding it sideways into a free column. New widgets (and ones moved to another page) now ask the grid to find the first actually-free spot instead, which is what lets a row of several compact tiles pack in neatly beside each other the way the screenshots above show, rather than stacking one under another with blank space to their side.
- Fix: **a page could be scrolled down well past its last widget, into visibly empty space**. In practice this traced back to the same one-column-mode bug above - once a page is an honest multi-column grid at every width, its own height already matches its content exactly, so there's nothing left to scroll into; a small `overscroll-behavior-y: contain` was added on top so iOS's own elastic bounce at the bottom edge stays a visual spring-back on that one page instead of being able to chain into anything behind it.
- New: **fullscreen popups now animate in** - a room's live view and its setup screen, Frigate's live camera view, and the widget store all get a quick, subtle "pop": a fast scale-up-from-slightly-smaller plus fade, eased with a touch of overshoot so it reads as springing open rather than just appearing. Nothing dramatic, just enough of a transition to feel intentional. The Group widget's own folder-style popup already animated in this same spirit (growing out of the exact tile you tapped); the rest of the app's popups now share that same "nice" feeling, just without the tap-point targeting Group's bubble needs.

## 0.09.019

- Fix: **weather widget showed no forecast boxes at all on current Home Assistant versions**. It was reading forecast data straight off the weather entity's own state (`attributes.forecast`) - which is how older HA versions exposed it, but core has since moved that data behind an explicit `weather.get_forecasts` service call instead (roughly core 2023.9 onward), so on any current instance that attribute is simply gone and the widget had nothing to show. ## 0.09.018

- Fix: **every widget was missing the gap around it, and had a odd dark "square" shadow in its corners**. Root cause was a CSS conflict: GridStack positions each widget's content by insetting it from all four edges of its grid cell (that inset is what creates the visible gap), but the widget's own card also had an explicit `width: 100%; height: 100%` rule meant for a completely different place it's reused (the small pinned-widget dock at the bottom, which does need that). Fixed with a more specific rule that only applies where a widget is actually sitting inside a GridStack grid, leaving the dock's own sizing untouched. This also fixes the exact same issue for widgets nested inside a Room or Group (e.g. two lights placed side by side inside a room) - those had it too.

It's now included alongside GridStack's own CSS.

## 0.4.0

- New: **Widget store**. A "Widgets" button in the toolbar (edit mode) opens a store listing every widget bundled with the add-on, each with an icon, localized name/description, and an on/off switch. Installing a widget loads its code and makes it usable immediately (no reload); uninstalling removes it from "+ Add widget" without touching widgets of that type already placed on your dashboard. New widgets shipped in future updates appear in the store automatically.
- New backend endpoints `GET/POST /api/widgets/installed`, persisted to `/data/widgets.json`. On first run (or upgrading from a version before the store existed) every bundled widget starts installed, so nothing changes for existing dashboards until you choose to trim it down.
- Widget JS/CSS is no longer loaded unconditionally for every widget on every page load — only installed widgets are fetched, via a small on-demand loader (`frontend/js/widget-catalog.js` + `LL.loadWidgetAssets`).
- A dashboard widget whose type is no longer installed now shows a friendly "not installed" placeholder with a shortcut back into the store, instead of an unhelpful "unknown widget" error.
- Repository description, README, and DOCS are now in English; the dashboard's own UI keeps following Home Assistant's configured language as before (English, Danish, German, Swedish, Norwegian).

## 0.3.0

- New widget: **Room** — one room per widget. When added, it first asks for a name, then which entities belong to the room (a searchable, grouped list). Entities are auto-grouped on display: Lights, Switches, Climate, Blinds & covers, Ventilation, Speakers & media, Robot vacuum, Security (door locks + door/window/motion sensors), Sensors (temperature/humidity etc.), and Other (scenes/scripts).
- Compact view on the dashboard: room name, temperature if available, and small icon badges per group — with a background color unique to each room name that lights up when a light in the room is on.
- Clicking a room opens it in a rounded pop-up (not edge-to-edge like the camera widget) with real controls: light on/off + dim, switch on/off, blinds up/stop/down, thermostat temperature up/down, speaker play/pause + volume, lock/unlock, and a run button for scenes/scripts. Sensors and security status are shown read-only.
- New backend endpoint `POST /api/hass/service/:domain/:service`, proxying to Home Assistant's service-call API — this is what makes control in the Room widget possible.
- Fix: `saveLayout()` could occasionally throw a console error if a debounced layout save ran right after a widget was removed. Layout serialization now safely skips any widget no longer in the DOM.

## 0.2.0
